# 面试课讲课细则

本文是通用 lesson-guide.md 之上的面试课补充。分段长度、插话、续学、调整大纲、对话里的图都照通用细则。

## 1. 一段怎么写

- 一段只讲一个点：一个概念、一个接口、一个取舍、一个步骤。
- 结构：一句结论 → 两三句展开（为什么、怎么做）→ 可选一句「面试时可以这样说：……」。讲师口吻里多用这句，它是学习者最后要带走的话。
- 讲接口、报文、表结构的那一段，直接把产物贴出来，再用两三句话讲关键字段为什么这样定。

示例（一段）：

```text
**为什么要用 Kafka 把上报和计费解耦？**

结论：上报量远大于扣费能力，而且有明显峰值，同步调用会把计费的故障直接传给业务。

  业务服务 ──用量事件──▶ Kafka ──▶ 计价引擎 ──▶ 余额服务

业务只负责把用量事件可靠地写进 Kafka；计费按自己的节奏消费。计费慢了，事件在队列里排队；计费挂了，业务不受影响，恢复后追平。

面试时可以这样说：「我先用 MQ 把上报和计费解耦，这样峰值被队列吸收，计费故障也不会传导到业务。」

页面上已经长出了 Kafka 和计价引擎。这里有疑问吗？没有的话我接着讲计价引擎为什么能横向扩。
```

## 2. 生长面板每课加什么

开课时写本课的生长增量，版面已经在写大纲时规划好（outline-patterns.md），同一节点的位置不变。

`diagram`（系统设计，或知识点的概念框图）：

- 概念课画出「调用方 + 黑盒」，黑盒用 `ghost` 节点。
- 架构课拆出主干，黑盒在这一课用 `until` 移除。
- 每个组件课加上这个组件自己的存储、依赖和连线。
- 核心链路课挂一条 `routes`，给一次请求经过的组件标号。
- 非业务能力课加旁路组件（死信队列、对账任务、降级通道）。
- 面试串讲课再挂一条按讲述顺序标号的 `routes`，接替核心链路课那条。
- **每课优先加节点和连线**，标注只放关键参数。课程后半段如果只在加标注，说明这些课没有讲出新结构。

`code`（知识点的写法演进，或经历复盘里的 SQL、配置改动）：讲到哪一版就加哪一版，每版写完整内容。

`timeline`（经历复盘）：定位过程每一步一个事件，结果与数据那一课的事件带上前后对比的指标。

## 3. 组件课与核心链路课（系统设计）

系统设计课最容易停在结论上：整课都是「要解耦」「要保证幂等」，学完画不出接口、写不出表。组件课和核心链路课用固定结构避免这一点。

### 组件课：四步

| 步骤 | 讲什么 | 课末写成什么卡 |
|---|---|---|
| 职责 | 管什么、不管什么、拥有哪些数据 | `points` |
| 接口与数据结构 | 对外接口、报文、表结构或状态机 | `code`（**必须有**） |
| 关键设计 | 最难的一两个点怎么解决、为什么这样解决 | `points` 或 `steps`，可以再配一张 `code`（伪代码） |
| 选型 | 至少两个候选、选哪个、什么情况下会换 | `compare` |

- **每课至少一份具体产物**：接口定义、请求 / 响应报文、schema、建表语句、伪代码之一。在对话里贴出来讲，课末写进 `code` 卡，`language` 填实际语言（`http`、`json`、`sql`、`proto`、`lua`、`go`、`text`……）。
- **流程图不算产物**：`language: "mermaid"` 的 `code` 卡不满足这条要求。课程页不渲染 mermaid，结构和流程已经由 `diagram` 面板表达。
- 产物要**能照着写**：字段名、类型、主键和唯一键、错误码都写出来。「扣费接口，入参是账户和金额」不算，下面这样才算：

```http
POST /internal/v1/accounts/1001/charges
{
  "event_id": "evt-1001-20261103101502-7f3a",
  "amount": 18000,
  "rule_version": 12,
  "occurred_at": "2026-11-03T10:15:02+08:00"
}

200 { "ledger_id": 880001, "balance_after": 49982000 }
200 { "ledger_id": 880001, "balance_after": 49982000, "duplicate": true }   重复请求：返回第一次的结果
402 { "code": "INSUFFICIENT_BALANCE", "balance": 5000 }                     余额 + 透支额度不够
```

- **要点写做法和依据，不写口号**。「扣费要保证幂等」是口号；「幂等靠流水表 `(account_id, event_id)` 唯一键：重复请求插入失败，查出第一次的流水返回」才是要点。
- 选型放在最后一步，因为前三步讲清了这个组件要解决什么问题，候选方案才有比较的标准。结论里带上「什么情况下会换」。

### 核心链路课：按时间线走一遍

- 挑一次具体的请求，给它真实的值（账户 1001、用量 1500、单价多少），从第一跳带到最后一跳。
- 一跳一段：到了哪个组件 → 收到什么 → 做了什么 → 写了什么、状态怎么变 → 发给下一跳什么。
- **每个组件都要经过**，并且只用组件课已经给出的接口和表。走的时候发现缺字段、缺状态，回到对应的组件课补上（更新那一课的 `code` 卡）。
- 开课时在 `diagram` 面板挂一条 `routes`（`lesson` 填本课 id），页面按顺序在组件上标 1、2、3……
- 正常路径走完后，挑一个故障点重走一遍（「第 5 跳之后服务崩了，重试时每一跳发生什么」），给后面的非业务能力课留钩子。
- 课末卡片：`steps`（每一跳一句话）+ 至少一张 `code`（这次请求在各跳的报文和落库数据）+ `points` + 标题为「面试怎么讲」的 `quote`。

## 4. 面试题

每道面试题都是本课的一次检验。发题、作答、「直接讲」、讲解、写卡的流程见 TEMPLATE.md「面试题就是本课的检验」，这里讲出多少、出什么、怎么写评分标准。

### 数量和位置

- **组件课 2–3 道**：一道概念题、一道设计题，加一条追问链。时间紧时概念题和设计题可以只留一道，追问链不省。
- 其他课至少一道：概念课和需求课出概念题，核心链路课出一道跨组件的题，非业务能力课适合做追问链。知识点和经历复盘的课同样至少一道。
- **穿插在段落之间**：讲完哪一步就问哪一步。讲完职责问概念题，讲完接口或关键设计问设计题，讲完选型做追问链。不攒到课末一起问。
- 一次只抛一道题，一题只问一个问题。

### 三种题型

| 题型 | 问什么 | 例子 | 课末写成 |
|---|---|---|---|
| 概念题 | 是什么、为什么需要、和相近概念的区别 | 「什么是超扣？根因是什么？」 | 标题为「面试题」的 `problem` 卡 |
| 设计题 | 让学习者自己给出接口、表或方案 | 「扣费接口要带哪些字段？重复请求返回什么？」 | 标题为「面试题」的 `problem` 卡 |
| 追问链 | 同一个点连问三层，每层接着上一层的回答问 | 见下文 | 标题为「追问链：xx」的 `qa` 卡 |

只出「xx 挂了怎么办」这类场景题，等于漏掉了前两种：概念题检查学习者是不是真的懂这个词，设计题逼学习者自己把产物写出来。

三种题都是主观题，`practice` 条目都要写 `rubric`，写法照通用细则「评分标准怎么写」：

- 概念题：列出定义、根因、区别里必须说到的几点，写明门槛。
- 设计题：列出产物里必须有的东西，如「带幂等键 `event_id`；重复请求返回第一次的结果而不是报错；余额不足有单独的错误码」。
- 追问链的每一层：只写这一层要答到的点，不把后面几层的答案写进来。

### 追问链

真实面试里，面试官不会问完一道题就换话题，而是顺着回答往下挖。追问链练的就是这个。

- 起点选本课的关键设计或选型。三层的方向：第一层问做法，第二层问这个做法在故障或并发下会怎样，第三层问极端情况、代价或替代方案。
- **一层一层问**：每层是 `practice` 里单独的一条，按面试题的流程走完（发题 → 停下 → 评分或「直接讲」→ 讲解），再接「顺着这个回答，面试官多半会追问：……」，发下一层。不三层一次抛出。
- 学习者的回答偏离了预设的方向，就顺着学习者的回答追问，下一层的 `q` 和 `rubric` 按实际要问的写；课末写卡片时再整理成一条完整的链。
- 课末写进 `qa` 卡：标题写「追问链：xx」，三条按顺序排，`q` 开头标 ①②③。

```json
{ "type": "qa", "title": "追问链：防超扣", "items": [
  { "q": "① 两个扣费请求同时到达同一个账户，怎么保证不超扣？", "a": "检查余额和扣减放进一个 Lua 脚本，Redis 单线程执行，中间插不进别的命令。" },
  { "q": "② Redis 扣成功了，写流水之前服务崩了，怎么办？", "a": "上游没收到成功就不提交 offset，Kafka 重投；Lua 里按 event_id 认出重复请求，不再扣，只把流水补上。" },
  { "q": "③ Redis 主从切换丢了最近一秒的扣减，余额比实际多了，怎么发现、怎么修？", "a": "MySQL 里的流水和余额是账本：对账任务比对两边，以 MySQL 为准覆盖 Redis；这期间多放行的金额由透支额度兜住。" }
] }
```

### 「面试题」卡

单独的概念题和设计题，讲解课末写成一张 `problem` 卡，跟在它对应的内容后面：

```json
{ "type": "problem", "title": "面试题", "question": "什么是超扣？根因是什么？", "approach": "先下定义，再讲根因，最后一句带出怎么防。回答结构：定义 → 根因（读和写之间有空隙）→ 防法。", "answer": "超扣是账户被扣成负数或超出透支额度。根因是「检查余额」和「扣减」分成了两步，两个并发请求都在扣减前读到了足够的余额。防法是让检查和扣减成为一个原子操作，比如放进同一个 Lua 脚本，或者用带条件的 UPDATE。" }
```

### 出题方向

- 系统设计：
  - 概念题：「xx 和 yy 有什么区别」「为什么需要 xx」「至少一次和恰好一次差在哪」
  - 设计题：「这个接口要带哪些字段」「这张表的唯一键怎么选」「状态机有哪几个状态、谁能触发」
  - 追问链的起点：「怎么保证不重不漏」「xx 挂了怎么办」「量涨 10 倍怎么办」「为什么不用 yy」
- 知识点：「底层怎么实现」「什么时候用 / 不用」「和 xx 有什么区别」「踩过什么坑」。
- 经历复盘：「怎么定位到的」「为什么选这个方案」「效果怎么衡量」「如果重来你会怎么做」。

## 5. 面试串讲（最后一课）

开课时在 `diagram` 面板挂一条 `routes`，`lesson` 填串讲课 id，按讲述顺序给组件标号，它接替核心链路课的那条路线。`code` 或 `timeline` 为主的课按版本或事件的顺序讲。

写成卡片的内容：

- 讲述路线：`steps` 卡，每段带时长。
- 开场白：`quote` 卡，标题「开场白」。
- 每段要点：`points` 或 `table` 卡。
- 可能的追问及应对：`qa` 卡，从各课的追问链里挑最容易被问到的几条。
- 本课照样要有标题为「面试怎么讲」的 `quote`：整门课浓缩成的一句话。

本课的检验由学习者选：模拟面试一轮、只把开场白和讲述路线讲一遍、或跳过，怎么问、各自怎么记见 TEMPLATE.md「结课：面试串讲」。

### 模拟面试

**模拟面试**只走面试题流程的第 1、2、3 步：发题、评分或跳过。评分的结果可以先不讲；第 4 步的讲解并进全部问完后的统一点评；不写「面试题」`problem` 卡。

- 你扮演面试官，按讲述路线一段段追问；每次只问一个问题，写进 `practice`，等学习者回答，然后直接问下一个。
- 全部问完后统一点评：讲述结构是否清晰、有没有遗漏关键点、哪里可以更简洁，没答好的题讲答题思路和参考回答。只评缺口，不打分。
- 没答好的问题按通用规则进 `review`。

`experience` 类主题：串讲开始时提醒「这是示范案例，面试前请把背景、数字和你的角色换成自己的真实经历」，并列出需要替换的要素。
