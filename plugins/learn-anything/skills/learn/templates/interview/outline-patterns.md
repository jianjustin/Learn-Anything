# 面试课的大纲骨架

骨架只是起点：按主题增删、合并、拆分，**突出重点**，非重点标「可选」。课数不限，以覆盖重点为准；**最后一课固定为「面试串讲」**。

## 怎么判断重点

- 面试官最可能深挖、最能拉开差距的部分是重点：系统设计里是核心链路经过的组件（接口、数据结构、关键设计）和一两个非业务能力，知识点里是原理和典型场景，经历复盘里是定位过程和数据。
- 每个主题挑 2–4 个「非讲不可」的点重点讲，在大纲后面点名；外围组件、可观测性、相近方案对比等标「可选」。
- 一课只解决一个问题。一课讲不完就拆成两课。
- 主线课的顺序就是面试里的讲述顺序。系统设计是：概念 → 需求 → 架构 → 逐个组件 → 核心链路 → 非业务能力。
- **每课都要落到具体的东西上。** 写大纲时就想好这一课课末能拿出什么：一份接口、一张表、一段报文、一组数字。只拿得出「应该怎么做」这类结论的课，要么并进别的课，要么想好产物再列进大纲。

## system-design（系统设计）

默认生长面板：`diagram`，画系统架构。

讲法是**先整体，再逐个组件，最后用一条链路把组件串起来**：

1. 核心概念：这个领域的 4–6 个术语、它们之间的关系、这类系统难在哪（「调用方 + 黑盒」在第一课画出来）
2. 需求澄清：功能边界、量级、实时性和准确性要求；带 2–4 组容量估算的数字，每组数字推出一个设计结论
3. 系统架构：拆出主要组件和数据流（黑盒在这一课拆开）；用一张表列出每个组件负责什么、拥有什么数据，这张表就是后面组件课的目录
4. 逐个组件：**每个组件一课**，按一次请求经过的顺序排。每课固定四步：
   - 职责：管什么、不管什么、拥有哪些数据
   - 接口与数据结构：对外接口、报文、表结构或状态机，给出能照着写的产物
   - 关键设计：这个组件最难的一两个点（幂等、并发、顺序、超时……）怎么解决
   - 选型：用什么实现，至少两个候选、选哪个、什么情况下会换
5. 核心链路串联：挑最关键的一次请求（「一次扣费」「一次退款」），按时间线走过**每一个组件**，每一跳给真实数据：请求和响应长什么样、哪张表多了哪一行、状态怎么变
6. 非业务能力 / 生产化（按主题挑重点，可拆成多课）：故障降级、突发流量、一致性与对账、可观测性、灰度与回滚
7. 面试串讲

几条规则：

- **选型跟着组件讲，不单独成课。** 「为什么用 Kafka」是用到 Kafka 的那个组件课的最后一步；几个组件共用的选型，放在第一个用到它的组件课。把选型攒成一课，听的人已经忘了每个组件要解决什么问题。
- **核心链路排在组件之后。** 组件还没讲就走链路，只能讲到「请求进来 → 处理 → 返回」；组件都讲过了，链路才串得起每一个组件，每一跳才给得出数据。
- **容量估算并进需求澄清**；模块边界并进系统架构的组件表和各组件课的「职责」。两者都不单独成课。
- **组件课通常 3–6 课。** 核心链路经过的组件放主线；外围组件（管理后台、报表、通知）标「可选」或并进相邻组件；很小的部件（死信队列、缓存）跟着它所属的组件讲。
- **概念课什么时候省略：** 学习者明显熟悉这个领域时（自己说做过类似系统、开题时术语用得准确、或者点名只想深挖某个组件），省略概念课或标「可选」，用到的术语在那一课顺带解释。拿不准就保留，在大纲后问一句「概念课要不要跳过」。

### 规划 `diagram` 的版面

写大纲时就把整张图的格子排好，同一节点的位置在所有课里不变：

- 调用方放第 1 列，数据流从左到右；配置、规则类组件放上一行；存储、旁路放下一行。
- `col`、`row` 从 1 开始，可以用 0.5 这样的小数微调：旁路组件要错开半行时写 `row: 2.5`；`span` 是占几列，正整数。微调时别让两个节点的框叠在一起。
- 第一课的黑盒是一个 `ghost` 节点，可以先占住后来组件的位置。
- 给旁路组件（死信队列、对账任务、降级通道）留出位置，它们在非业务能力课才出现。

每课开课时往图里加什么，见同目录 lesson-guide.md「生长面板每课加什么」。

## knowledge（知识点 / 八股）

默认生长面板：`code`，放写法的逐版演进；偏原理、不适合写代码的知识点（MVCC 版本链、GC 三色标记、Redis 持久化等）改用 `diagram` 画概念框图。两个面板可以同时用。

1. 是什么、解决什么问题
2. 底层原理
3. 典型场景：从一个具体 case 出发
4. 写法演进：从最小可用写法一步步改进
5. 常见坑
6. 与相近方案对比（可选）
7. 面试串讲

## experience（经历复盘）

默认生长面板：`timeline`，放排查时间线，可带指标；涉及 SQL、配置或代码改动时再加一个 `code` 面板。

用**示范案例**：自己构造一个典型案例（背景、现象、指标都是示范数据），不追问学习者的真实经历。大纲上方、开题对话、面试串讲开头和课程页的 `notice` 都要标明「示范案例，请换成你自己的经历」。

1. 背景与现象：系统规模、问题现象、业务影响、你的职责
2. 定位过程：从现象到根因，每一步看了什么、排除了什么
3. 解决手段：做了哪些改动、为什么这样选
4. 结果与数据：前后对比的数字
5. 反思与预防：根因、以后怎么提前发现
6. 面试串讲（按 STAR 结构，3–5 分钟）

## 大纲在对话里的写法

整体格式照 kickoff.md 第 6 节（模板一行、上法、资料、大纲、slug），大纲部分按下面写。示例（系统设计，每行末尾的延伸阅读照通用格式写，这里省略）：

```text
大纲（共 13 课）：
1. 核心概念 —— 计量、计价、扣费、出账四个词，以及余额和流水的关系
2. 需求澄清 —— 计什么费、多实时、量多大；三组数字推出要削峰、要聚合
3. 系统架构 —— 拆成采集 → 计价 → 扣费 → 出账四段，列出组件表
4. 组件：用量采集 —— 上报接口和事件格式、去重；为什么用 Kafka
5. 组件：计价引擎 —— 规则表、按事件时间取版本；规则放配置中心还是数据库
6. 组件：余额服务 —— 扣费接口、原子扣减防超扣；余额放 Redis 还是 MySQL
7. 组件：流水与账单 —— 流水表、幂等键、汇总出账；单库分表还是分布式数据库
8. 核心链路：一次扣费 —— 一条用量事件从上报到出账，每一跳的报文和落库数据
9. 故障降级 —— 每个依赖挂了怎么办
10. 突发流量 —— 三层吸收峰值（可选）
11. 一致性与对账 —— 流水是账本，对账兜底
12. 可观测性 —— 三类核心指标（可选）
13. 面试串讲 —— 串成 10 分钟讲述路线

重点是 6、7、8：面试官最常深挖扣费怎么防超扣、流水怎么不重不漏；第 8 课把所有组件串成一条讲得出来的链路。
概念课要不要跳过？
```

- 每课一行：标题 + 一句话。
- 组件课的一句话点出这课要给的产物和选型问题（「扣费接口、原子扣减防超扣；余额放 Redis 还是 MySQL」），不写「介绍余额服务」。
- 大纲后用一两句话说明哪几课是重点、为什么。
- `experience` 类在大纲上方加一句：「下面用一个示范案例来讲，请在面试前换成你自己的经历。」
- 课程 id 用英文 kebab-case，取自标题，如 `requirements`、`balance`、`core-flow`、`pitch`。
